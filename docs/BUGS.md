# BUGS

Known bugs and risks, each verified by Claude in the code or the primary source (Decision 26) unless it says "unverified". Claude is the only writer. A verified bug becomes a card when the owner picks it; remove the entry when its card merges. Test-report fails (pass or fail, card number, screenshot) are added here or become a card.

- **Merge restore can roll back newer local edits (verified in the code 2026-10-31 at `main` `0b444a3`, not carded).** `restoreFullBackup` in `src/io/backup.ts`: when a card with the same `uuid` already exists, `merge` and `overwrite` both call `db.cards.update` with the backup's `cardData`, `modification_date`, `embeddedAssets` and `snapshots`, with no comparison of dates. Merging an older backup replaces newer local work, including its snapshot list. Unverified: what the restore screen says "merge" does.
- **Storage limits can reject real-world cards (verified 2026-10-31, not carded).** `src/schemas/limits.ts` caps personality, scenario, creator and character_version at 2,000 characters, extensions at 200,000 characters (string length, not bytes), a lorebook entry's content at 20,000, 50 keys per entry, tags at 50 characters, names at 100 and the avatar data URI at 10 MB. The Dexie hooks in `src/db/index.ts` run the strict storage schemas on every add and update and throw past a limit. Import reads cards with the loose schema, so a card can be read and then fail at save; an autosave that fails shows "Save failed" (`saveActiveCardMetadata`). Unverified: how many real cards exceed a cap, what the import screen shows, whether the editor fields have their own length limit. Needs a real-card fixture.
- **Connection profile fields that do nothing, and `customHeaders` in "no API keys" backups (verified 2026-10-31, not carded).** `customHeaders` and `frequencyPenalty` appear only in the profile type (`src/db/index.ts`), the backup schema and the settings form `ConnectionProfilesSection.tsx` (code search), and `src/services/llmAdapter.ts`, read in full, uses none of `customHeaders`, `topP` or `frequencyPenalty`, so they are never sent to a provider. `systemOverride` and `contextLimit` were not checked. Also, `createFullBackupJson` (`src/io/backup.ts`) removes only `apiKey` when keys are left out: `customHeaders` (free text that may hold an `Authorization` value) and `baseUrl` (`validateAndCleanBaseUrl` blocks embedded user and password, not query-string tokens) stay in the file. Card 038 part B (merged, PR #37) titles that dialog "Export Backup (no API keys)", which is true for the keys only. Options for the owner: strip `customHeaders` in that case (`src/io`, `Review: required`), or remove the dead fields.
- **Provider stream errors are swallowed and requests cannot be cancelled (verified 2026-10-31, not carded).** `src/services/llmAdapter.ts`: the OpenAI-style and Anthropic stream loops handle only content, usage and `[DONE]` events. An `error` event in the middle of a stream is dropped, and the partial text is returned as a normal result and counted in the cost tracker; a JSON parse failure is ignored (`catch {}`). No request has an `AbortSignal` or a timeout (`LLMRequestOptions` has none). The Gemini path goes through the SDK and was not checked.
- **Fallback profiles receive the card text without a notice (verified in the code 2026-10-31; callers not checked).** `sendLLMRequest` in `src/services/llmAdapter.ts` tries each profile in order with the same messages and returns the first success. Decision 7 says every request shows "Sent to <provider>". Unverified: whether any caller passes more than one profile, and what the screen shows.
- **Smaller code issues (verified 2026-10-31, not carded).** (a) `src/io/backup.ts`: in a restored ZIP, a folder `assets/__proto__/...` makes `zipAssetsMap[cardUuid]` the shared `Object.prototype`, and the asset is written onto it; use `Object.create(null)` or a `Map` (low; needs a hand-made backup). (b) `createFullBackupJson` leaves out an asset whose stored shape it cannot read, with no warning. (c) A ZIP backup holds each asset twice (base64 in `backup.json`, raw in `assets/`); memory on phones is unmeasured. (d) The 200 MB cap measures the input only; ZIP contents are not size-limited when unpacked.
- **CI and config hygiene (verified 2026-10-31, not carded).** CI runs Node 20, which reached end of life on 2026-04-30 (endoflife.date/nodejs); `README.md` still says "Node.js 20+". `.github/workflows/ci.yml` has no `permissions:` block. `eslint.config.js` registers `jsx-a11y` but enables none of its rules, and lint warnings never fail CI (43 in Muse's run on PR #36). Leftovers: `wrangler.toml` (name "cardcrucible"), `metadata.json` (claims a server-side Gemini API; the app has no server), `vite` listed in both `dependencies` and `devDependencies`, the `@` alias in `vite.config.ts` and `paths` in `tsconfig.json` point at the repo root, the CSP allows `wss:` although `src/` has no WebSocket, and the CSP exists in both `vercel.json` and `public/_headers` with HSTS only in `_headers`. A change to CI or deploy config is a `Review: required` card.

- **Backup restore skips some items without telling the user (verified in the code 2026-10-31 at `main` `12864aa`, not carded).** `restoreFullBackup` in `src/io/backup.ts`: a lorebook or connection profile without a `uuid` is skipped with no count and no message (a card without one is counted in `cardsSkipped`); a failed settings write is swallowed (`// ignore`); in overwrite mode the old cards, lorebooks and profiles are cleared before the new ones are added, so an item that fails to save is simply absent afterwards and is reported only in `errors`. Unverified: whether the restore screen shows `errors`, and whether a card rejected by the Dexie hook leaves the surrounding transaction intact. Files written by the exporter always carry a `uuid`, so mainly hand-edited backups are affected. Cards and lorebooks do go through the Dexie validation hooks on restore; profiles and settings have none by design.

- **Lorebook simulator budget order is the reverse of SillyTavern (verified in the code; the ST side is research 001 claim 2, not re-read).** `src/utils/lorebookScan.ts` sorts activated entries by weight, then `a.order - b.order`, then fills the token budget until the first overflow; research 001 says SillyTavern sorts `b.order - a.order` (higher `order` survives, low numbers drop first). `lorebookConflict.ts` also sorts by order ascending, for conflicts. Not carded; Task 024 covers the warning wording only.
